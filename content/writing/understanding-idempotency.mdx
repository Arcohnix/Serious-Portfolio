## The Illusion of Exactly-Once Delivery

In distributed systems engineering, one of the most persistent misconceptions is that transport layers can guarantee exactly-once message delivery on their own.

Networks are inherently asynchronous and prone to failure:
- TCP packets can be delayed or dropped.
- Workers can crash immediately after processing an order but before committing their consumer offset.
- Upstream payment gateways can execute a capture successfully while the acknowledgment response times out over the wire.

When a client or producer experiences a timeout, its only safe operational posture is to retry. Because retries happen under unpredictable network conditions, **duplicate delivery is a certainty, not an edge case**.

> If your downstream business logic cannot safely execute the same payload multiple times without changing the resulting system state, your pipeline is not resilient.

## Why Deduplication at the Transport Layer Fails

Many teams attempt to solve duplicates by storing processed message identifiers in an in-memory cache such as Redis. While fast, this introduces two dangerous failure modes:

1. **The Cache Eviction Window**: Under memory pressure or cache TTL expiration, previously seen message keys are evicted. When a slow retry arrives minutes later, the system treats it as new and executes duplicate side-effects.
2. **Dual-Write Inconsistency**: If the message key is saved to Redis, but the database transaction fails right after, subsequent retries will be falsely rejected as duplicates, leading to silent message loss.

True idempotency must be anchored to the source of truth: **the transactional database engine**.

## The Transactional Outbox & Natural Idempotency Keys

To guarantee consistency without two-phase commit overhead (which cripples throughput and availability), we couple state changes with event production through a database transaction:

```sql
-- 1. Create table with unique idempotency constraint
CREATE TABLE idempotency_records (
    idempotency_key VARCHAR(64) PRIMARY KEY,
    entity_id VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL,
    response_payload JSONB,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 2. Atomic check-and-insert in the same transaction
INSERT INTO idempotency_records (idempotency_key, entity_id, status)
VALUES ('ord_tx_981a2f', 'ord_10482', 'PROCESSING')
ON CONFLICT (idempotency_key) DO NOTHING;
```

If the `INSERT` returns zero affected rows, the worker knows immediately that this transaction is already inflight or completed. It fetches the existing record and returns the cached outcome without repeating the underlying mutation.

## State Machine Transitions

A resilient pipeline treats the lifecycle of an entity as a strictly ordered state machine:

| Initial State | Event Received | Target State | Duplicate Action |
| :--- | :--- | :--- | :--- |
| `PENDING` | `PROCESS_ORDER` | `PROCESSING` | Return inflight status |
| `PROCESSING` | `PAYMENT_SUCCESS` | `COMPLETED` | Return existing receipt |
| `PROCESSING` | `PAYMENT_TIMEOUT` | `FAILED` | Return cached failure |
| `COMPLETED` | `PROCESS_ORDER` | `COMPLETED` | No-op idempotent return |

By enforcing explicit transition guards (`WHERE current_status = 'PENDING'`), out-of-order retries or delayed duplicate messages can never regress an already completed entity.

## What Happens During a Downstream Crash

Consider what occurs when a worker dies mid-execution:

```typescript
export async function executeOrder(
  idempotencyKey: string,
  payload: OrderPayload
): Promise<OrderResult> {
  // Begin atomic database transaction
  const client = await pool.connect();
  try {
    await client.query("BEGIN");

    const record = await client.query(
      `INSERT INTO idempotency_records (idempotency_key, entity_id, status)
       VALUES ($1, $2, 'PROCESSING')
       ON CONFLICT (idempotency_key) DO NOTHING
       RETURNING *`,
      [idempotencyKey, payload.orderId]
    );

    if (record.rowCount === 0) {
      // Duplicate delivery detected: load cached state
      const existing = await client.query(
        `SELECT status, response_payload FROM idempotency_records WHERE idempotency_key = $1`,
        [idempotencyKey]
      );
      await client.query("COMMIT");
      return existing.rows[0].response_payload;
    }

    // Execute domain mutation
    const result = await processInventoryAndCharge(client, payload);

    await client.query(
      `UPDATE idempotency_records SET status = 'COMPLETED', response_payload = $1
       WHERE idempotency_key = $2`,
      [JSON.stringify(result), idempotencyKey]
    );

    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}
```

If the worker crashes prior to `COMMIT`, the database rolls back the transaction entirely. When a replacement worker consumes the retried event, the idempotency record does not exist yet, allowing clean, atomic re-execution.

## Key Engineering Takeaways

- **Deduplication requires transactionality**: Never separate your idempotency check from the database transaction executing the mutation.
- **Client-provided idempotency keys**: Have upstream clients supply a UUID or deterministic hash per intention.
- **Model failure as a first-class state**: The best distributed systems are not those that never fail, but those that make repeated failure safe.
